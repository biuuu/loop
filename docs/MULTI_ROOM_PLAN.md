# 无密码身份与多房间规划

状态：主链路已实施，2026-11-14。最新调整：临时身份也能创建房间，邮箱相关 UI 隐藏，后端认证能力保留。以下邮箱/第三方设计作为保留能力或后续规划，不代表当前界面入口。具体验证见 PROGRESS。

## 已确认需求

- 主要入口是仅填写用户名创建临时账号；支持邮箱验证码登录，不提供密码登录。
- GitHub/Google 登录为可加入的扩展。跨设备和丢失浏览器身份后的访问通过已绑定邮箱/第三方身份恢复，不做密码找回或恢复码。
- 每位用户最多拥有一个持久房间；房主离线不删除房间。2026-11-16：新用户创建时自动建房，默认“昵称的房间”、5 个舞台位置（最初为 6 个）、随机环境；无指定目标房间时自动进入自己的房间。
- 增加房间列表页，可以选择进入不同房间。
- 房主拥有自己房间的管理权限。
- 房间属性包含名称、环境；2026-11-15 追加多个预设环境需求。
- 保持 Vue/PixiJS、单 Node 服务、SQLite/direct SQL 和浏览器直连音频。

## 实施默认值

- 用户最新确认：临时账号也可以创建房间；仅要求有效身份，不要求验证邮箱。界面隐藏邮箱登录、绑定、账号邮箱及相关提示。
- 临时账号的用户名只是昵称，可以重名，不是登录凭据。未绑定身份时清除 Cookie 会失去对原资料/房间的访问，不能靠再次输入同名恢复。绑定后保留用户 ID，不新建一份歌单或房间。
- 一人一房落实为每个用户 ID 一个房间，数据库唯一约束兜底；身份创建、验证码和建房均限流。
- 建议个人歌单、猫咪外观属于用户，跨房共用；位置、席位、播放、表情属于房间。
- 同一用户全站最多一个有效房间连接，延续目前替换旧标签页的行为。拥有房间不限制访问别人的房间。
- 每房暂用 30 人，房主可配置 1–6 个舞台位置，默认 5 个；座位及舞台 UI 同步自适应。少于台上人数时须先下台再保存。房间名称建议 1–32 字，环境白名单为 `cozy`、`greenhouse`、`seaside`、`rooftop`，默认 `cozy`。
- 房间公开出现在大厅；第一版不做密码房、邀请链接权限、私密房、共同房主、所有权转让；多个预设美术场景已按后续需求追加。
- 房主可以暂停新访客进入，已有成员及其短时重连不被清退；房主自己可以进入。该状态不等同于暂停音乐。
- 空房保留数据库资料；所有成员及断线保留期结束后停止播放、释放运行状态。以后重新进入从空舞台开始；重启同样保留资料、清空实时状态。

## 页面与使用流程

1. `/` 为大厅：房间名称、房主昵称、环境、在线人数/容量、是否可进入；可显示当前曲目的一行简要信息，不返回音频 URL 或完整歌单。
2. 大厅主入口为填写昵称进入，当前隐藏邮箱及其他登录方式入口；身份菜单提供退出，新用户自动建房；若有目标房间链接，创建身份后进入目标房间，否则进入自己的房间。“我的房间”位于大厅，旧身份尚无房间或删房后可手动创建，已有房间不能重复创建。
3. `/{number}` 为可分享、可直接打开的数字房间地址，旧 `/rooms/:roomId` 链接保留并在进入后规范为数字地址。房间改名不影响地址。不存在/删除/满员/禁止进入分别提供明确反馈与返回大厅入口。
4. 房间内保持全屏猫咪场景，增加房间名、返回大厅按钮；房主可打开设置和成员管理。
5. 点击返回大厅是明确离房；台上用户离房/切房应确认会离开舞台。刷新、短暂网络中断使用现有 30 秒保留期。浏览器后退离开房间也执行完整清理，不能让旧房音频留在后台。
6. 默认用小型 History API 路由模块处理大厅与房间两种路径及 popstate；账号表单作为共用弹窗。第三方 OAuth 回调由服务端处理，成功后返回白名单内的站内路径。服务端已有 SPA fallback，但需测试直接访问房间路径。
7. 列表先使用分页 HTTP 摘要，默认每页 24 条，页面可见时约 15 秒刷新并提供手动刷新；不将房内移动广播给大厅。按在线人数降序、创建时间/ID 稳定排序。在线人数只统计连接中的用户，是否已满以包含保留席位的实际准入判断为准。

## 房主权限边界（建议第一版清单）

| 操作                            | 普通成员 | 房主         |
| ------------------------------- | -------- | ------------ |
| 移动、表情、管理自己的歌单/外观 | 可以     | 可以         |
| 正常上台、下台                  | 可以     | 可以         |
| 跳过自己的当前曲目              | 可以     | 可以         |
| 跳过房间当前任意 DJ 的曲目      | 不可以   | 可以         |
| 修改房间名、选择允许的环境      | 不可以   | 可以         |
| 暂停/恢复新访客进入             | 不可以   | 可以         |
| 让指定成员下台                  | 不可以   | 可以         |
| 将成员移出房间                  | 不可以   | 可以         |
| 封禁/解封成员在本房间的进入资格 | 不可以   | 已纳入       |
| 删除房间                        | 不提供   | 不提供       |

- 踢离与封禁分开：踢离后可以再次进入，封禁持续到房主解除；封禁仅针对该房间和该用户身份。
- 房主管理范围不包含别人的私人歌单、账号和其他房间。房主离线不转移所有权，不自动选举新房主。
- 不允许房主踢离/封禁自己；离房保留单独入口。全房暂停/恢复播放尚未纳入本轮，若需要应另定义暂停时间线。
- 环境由服务端白名单校验，不接受任意资源 URL。环境选择持久化，通过已有 room:updated 同步；客户端只替换静态背景，所有环境共用活动范围和舞台坐标，不重做场景编辑器或坐标系统。
- 每次操作在服务端读取真实身份并核验 ownerId；客户端显示管理按钮不构成授权。执行排队操作时再次核验权限和目标成员会话。

## 无密码身份、会话与旧数据

- 保留现有用户 UUID 作为资料、歌单和房主归属的稳定键。现有 `guests` 暂作为资料表保留；新增 `auth_identities(user_id, provider, subject, created_at)`，唯一键为 `(provider, subject)`。provider 为 email/github/google；不新增密码字段或密码哈希依赖。
- 临时资料绑定尚未使用的邮箱/第三方身份时保留原 UUID、歌单、外观和房间。邮箱/第三方身份已属于另一用户时，普通登录进入该用户；绑定操作明确提示冲突，不静默合并资料、转移房间或根据相同昵称认领账号。
- 新增 `sessions`：只存随机会话令牌哈希、用户 ID、认证方式、过期时间；继续使用 HttpOnly/SameSite Cookie，生产 HTTPS 下使用 Secure。临时用户同样走服务端会话，登录/绑定轮换令牌，退出撤销当前会话并释放该房间会话。
- 首次绑定时撤销该资料的旧临时会话和原 guests.token_hash 访问通道，避免旧游客 Cookie 长期保有权限；当前连接重新建立已验证会话。后续邮箱登录默认不注销所有登录设备，但全站仍只允许该用户一个有效房间连接；账号设置提供“退出所有设备”。
- 邮箱验证码建议 6 位、5 分钟有效、每次最多 5 次尝试、同邮箱发送间隔至少 60 秒；这些为实施默认值。对 IP/邮箱/验证挑战分别限流，响应不暴露邮箱是否已有账号。重发使旧挑战失效；验证成功在事务内一次性消费，避免并发重复使用。
- 新增 `email_challenges` 保存邮箱、随机 challengeId、login/bind 用途、绑定发起者/会话、验证码 HMAC、到期时间和尝试次数。短验证码用服务端秘密参与 HMAC，不仅保存可穷举的裸摘要；验证码、Cookie、OAuth 令牌均不得进入日志、前端测试后门或房间事件。
- 绑定验证码必须在同一发起身份/会话中验证；输入邮箱或客户端标记 verified 均不能直接绑定。邮箱规范化不擅自移除点号或加号后缀。
- 发信模块只封装 SMTP/已选择发信服务的一种实现，测试注入替身；部署需配置发信凭据，真实交付另行验证。邮件未配置时保留临时入口，邮箱入口说明暂不可用，不伪装发送成功。
- 第三方身份独立绑定到 user_id，使用固定 provider subject：GitHub 用户数字 ID，Google 的 issuer/sub。不能以第三方昵称或邮箱自动合并已有用户。第三方身份绑定到现有账号需当前有效会话和重新认证，第一版不开放移除最后一种可恢复身份。
- GitHub 使用服务端授权码流程，state/PKCE 防护，最低登录权限；Google 使用 OIDC 并校验签名、issuer、audience、expiry、nonce。回调携带的绑定目的、发起会话和返回位置都由服务端保存，回调不能改变绑定目标。取到稳定身份后签发本站会话，首版不保存供后续调用的第三方 access/refresh token。
- GitHub/Google 可在邮箱与多房间主链路完成后接入，未配置 provider 不显示可点击按钮。需要分别注册应用及配置回调地址，不因某个 provider 未配置而阻塞主要入口。
- 官方协议依据：[GitHub OAuth 授权](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)、[Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect)。实施时使用维护中的协议库校验，不自行实现令牌签名验证。

## 数据与模块边界

- `rooms`：`id`、`owner_user_id`（关联资料的稳定 UUID，并设 UNIQUE）、`name`、`environment_id`、`join_policy`（open/closed）、`revision`、`created_at`、`updated_at`。绑定邮箱不改变房主键。另以 `room_numbers(number INTEGER PRIMARY KEY AUTOINCREMENT, room_id UNIQUE REFERENCES rooms ON DELETE CASCADE)` 分配持久数字地址，保留内部 UUID 与现有 Socket/管理 API 的身份关系。
- 若纳入封禁，新增 `room_bans(room_id, user_id, created_at)`，复合主键；删除房间级联删除封禁记录，不删除用户或歌单。
- `Room` 仍只负责一个房间：成员、位置、舞台、轮转、解析、计时器和房间内修订号。不得在单个 Room 内保存其他房间的成员。
- 新增 `RoomRegistry`：按房间 ID 延迟创建/释放 Room 实例；负责全站用户有效会话索引、切房准入、持久房间查找、摘要读取、移出/删除的协调。Store 只负责 SQL，app 负责 HTTP/Socket 边界。
- 每个新 Socket 握手携带目标 roomId，连接成功后房间绑定不可修改；切房建立新的连接。服务端频道使用 `room:<id>`，所有房间广播由 `io.emit` 改为目标频道广播。
- 房间快照及增量通知携带 roomId；客户端将 roomId 与本地递增的进入代次共同作为作用域，修订号只在当前房间会话内比较。个人歌单事件仍只发送给该身份当前有效连接，不放进房间广播。
- 房间资料变化用独立 `room:updated` 摘要；移动、播放、表情沿用已拆分的小事件，不退回整房间广播。被移出/删除用 `room:removed {roomId, reason}` 退出提示。
- Socket 命令目标房间从已验证的绑定取值，拒绝通过 payload 伪造房间或 ownerId。room:sync、skip 回执也补上当前会话检查。

## 必须先解决的生命周期问题

当前 `Room.enqueue` 会等待整个音频解析，`advance()` 返回后主要检查 closed；不能直接把踢人、离房加入现有等待队列。

1. 将“挑选下一曲/启动解析”和“验证结果/提交播放”作为短状态操作，网络等待放在状态队列之外。维护当前待解析 DJ、解析代次及可主动结束等待的取消句柄。
2. 解析结果提交时核验 Room 实例仍有效、解析代次仍有效、成员会话和上台资格仍有效，再原子轮转歌单并提交播放。loading 通知、失败遍历、finally 和轮转计时器均带同一代次保护。
3. 取消必须使调用方 Promise 结束，并清除本次超时/通知；不能仅清 timer 而让命令永久等待。上游请求可以尽力中止，但即使无法中止，晚到的成功或失败也不得修改任何状态。
4. 新增完整成员离开操作，与仅下台区分；清理成员、连接、断线保留、表情冷却、席位，并在其为当前或待解析 DJ 时推进播放。管理操作可处理正在断线保留的成员。
5. Registry 先检查目标房存在、开放状态、封禁及容量，再在一个不等待外部网络的状态变更内使旧会话失效、立即移除旧房成员、建立新房会话。失败时保持原房；连续切房只提交最后一次有效请求。
6. 客户端切房时可先等待新房准入结果，再替换原连接；成功后的提交路径统一清空旧快照、音频源、移动、表情、时钟样本及在途操作。失败保持原房可用。明确离房/被踢/删房必须立即清空旧快照，使音频停止；不能等新连接成功才清理。
7. 旧连接 disconnect、旧 grace timer、旧房解析、旧 HTTP/Socket ack 均只能影响原会话。A→B→A 时不能仅比较 roomId；客户端连接对象/进入代次和服务端成员会话令牌都需要校验。
8. 运行时房间释放与持久房间删除是两种操作。删除在 Registry 短状态操作内进行，不跨网络等待：检查权限、事务删除持久记录、撤销运行实例与准入资格，再通知/清理成员。数据库事务失败则保留原房；晚到结果通过实例/代次失效检查拒绝，不得重新创建房间。

## HTTP 与实时接口范围

- 身份：保留昵称临时身份入口；新增邮箱验证码请求/验证接口、绑定接口、退出/退出所有设备及当前身份摘要。OAuth 增加受白名单限制的 provider start/callback。身份摘要只返回登录方式/必要的脱敏邮箱，不返回验证码或认证秘密。没有密码注册、修改密码、密码找回接口。
- `GET /api/rooms`：分页目录；`GET /api/rooms/:id`：单房资料/准入摘要，也支持数字房号查询并返回内部 ID 与 number；管理接口仍使用内部 ID。
- `POST /api/rooms {name, environmentId}`：服务端从账号会话确定房主；唯一约束兜底并发重复创建。
- `PATCH /api/rooms/:id {name?, environmentId?, joinPolicy?, expectedRevision}`：房主编辑资料，用 revision 拒绝过期修改。
- 明确离房使用带 ack 的 `room:leave`；房间内管理命令建议 `stage:remove {userId}`、`member:kick {userId}`，skip 扩展为当前 DJ 或房主可用。
- 若采用封禁：房主专用封禁列表/添加/移除 API；添加封禁同时移除该房成员，其他房间不受影响。
- 所有修改接口沿用来源校验，并新增与操作匹配的限流；公开目录永不返回邮箱、登录状态详情、令牌、完整成员列表或个人歌单。

- GitHub/Google 作为阶段 6 后的可选登录扩展，复用阶段 1 的 auth_identities/sessions；新增 `server/oauth.ts` 与协议回调测试。配置应用凭据后再验证实际登录，不把第三方可用性作为多房间主链路的前置条件。

## 核心验收案例

- 两账号、两房间在同一席位编号同时播放，移动/表情/跳曲互不串房，个人歌单事件只到本人。
- 每人并发创建两次也只有一间房；非房主伪造设置、踢人、封禁、删除、管理员跳曲均失败。
- A→B→A、双标签同时进入不同房、目标房已满/关闭/删除、切换中断网、旧 ack 晚到；最多一份有效成员会话，失败准入不踢掉原房用户。
- 解析中强制下台、踢离、封禁、切房、删房，分别覆盖成功、失败及永久不返回的解析；动作及时完成、无旧歌启动、无额外歌单轮转、无残留 timer。
- 普通刷新可在 30 秒内恢复席位；明确离房立即释放，过期旧 disconnect 不清除新会话；房主离线不影响其他成员和持久所有权。
- 临时身份绑定邮箱后歌单/外观保持；登录其他账号不会混入游客数据；绑定时旧临时 Cookie/Socket 失效。再次输入同名不能访问别人的临时资料。
- 邮箱验证码过期/复用、错误次数、重发/并发验证、限流、跨会话绑定、已绑定身份冲突均有行为测试；真实邮件交付仅在配置后另行验证。
- OAuth 回调错误 state/nonce、过期、跨会话绑定、伪造 issuer/audience、subject 冲突、恶意返回 URL 必须拒绝；相同邮箱/昵称不自动合并用户。无 provider 配置时临时与邮箱入口仍可用。
- 旧数据库升级保留资料/歌单，迁移可重复执行；重启仅清空实时状态，账号、房间、所有权和封禁记录保留。
- 大厅刷新不订阅房内移动数据；已有移动/播放/歌单顺序增量消息仍保持精简。列表离开或后台时停止轮询。
